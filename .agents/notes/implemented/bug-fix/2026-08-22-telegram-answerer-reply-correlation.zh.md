# Agent Note: Telegram 回答者将回复关联到所问的问题

Status: implemented

[English](2026-08-22-telegram-answerer-reply-correlation.md) | 中文

## Problem

每次轮询都从 offset 零启动 `getUpdates`，因此 Telegram 会在每次询问时重新投递最近的未确认历史，而来自授权会话的第一条文本或按钮按下会回答恰好正在轮询的那个问题 —— 一条过期回复可以回答新提示，两个并发询问的发送与轮询会在同一会话上交错。发送也只检查 curl 的退出状态，因此 `{ok:false}` 信封（错误令牌、错误会话）会被当作已投递，而带令牌的 URL 出现在 curl 的命令行上，可从 `/proc/<pid>/cmdline` 读取。

## Decision

回答者为每个插件挂载保留一个串行化的机器人会话。在询问中首次发送之前，它通过探测 `getUpdates?offset=-1` 清空挂起的历史 —— 该调用只返回最新一条更新且不确认任何内容 —— 并把游标停在其后一位；游标随后跨轮询与询问持久保存。drain 失败会使询问封闭失败，让另一个回答者接手。

每条发出的问题生成一个不可预测的 nonce，嵌入消息文本和每个按钮的 `callback_data`，并且 `sendMessage` 的信封必须携带 `result.message_id`。按钮按下只在引用该消息 id 时被接受；自由文本回复仍接受自授权会话，因为清空之后只有比问题更新的更新才可能到达。Bot API URL 通过每次运行的环境条目而非 argv 传给 curl，非 ok 信封现在携带 Telegram 的描述抛出。并发询问在一个 promise 链后排队，其发送与轮询永不交错；排队的询问等前一个落定后才继续。

## Alternatives considered

**要求每条回复都是对所发消息的 swipe-reply。** 不采用，因为普通键入的回答 —— 这个会话的常见情况 —— 会静默地不再回答问题。

**把更新游标持久化到磁盘以跨越重启。** 不采用，因为每个进程在首次发送前本来就会重新建立 drain；持久化增加了状态却没有消除任何可达的过期。

**拒绝冲突 manifest 或把机器人访问移入常驻 worker。** 推迟 —— 相对审计指出的失效模式两者都是更大的重构；插件内的串行化会话已经消除了交错与重放。

## Verification

`telegram-answerer.spec.ts` 覆盖：按钮按下与所发消息 id 的关联及忽略过期按下；先 drain 后发送的顺序与跨连续询问复用游标不再探测；nonce 在文本与回调中的存在；并发询问的串行化（包括一次失败询问后的队列恢复）；`{ok:false}` 信封、缺失消息 id、传输失败与畸形更新按 deadline 封闭失败或重试；以及令牌绝不出现在命令行。

## Consequences

过期或跨问题的回复不能再回答提示，投递失败可见而不是被当作"已送达"。第二个并发问题会比以前更晚到达 Telegram —— 在前一个询问落定之后 —— 这是单个人类会话单一写者的代价。nonce 在消息文本中可见，给人类与代码相同的关联凭据。
