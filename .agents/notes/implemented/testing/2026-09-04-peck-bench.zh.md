# Agent Note: Peck Bench 模型比较

Status: implemented

[English](2026-09-04-peck-bench.md) | 中文

## 问题

直接比较模型会混杂模型质量与不同的智能体工具、提示、执行状态和评分器。有效的路由决策需要重复运行，并将模型选择作为唯一有意改变的变量，同时保留足够证据来检查失败，而不是相信单一汇总分数。

## 决策

模型比较使用公开 Python SDK 和一套由 benchmark（基准测试）拥有的 Harness 组合。每个模型都会获得全新的 fixture（测试前置数据）副本，以及相同的提示、工具、超时、输出上限和确定性外部评分器。初始矩阵包含 Omen Alpha 和 Muse Spark 1.3 Contributor；由于两者的 wire protocol（传输协议）不同，它们使用独立的 OpenCode Go 路由。

Benchmark 编排消费 Harness；它不是智能体能力。将其放在 `bench/` 下，可避免评分策略和提供方价格进入 agent loop（智能体循环）或已发布包。SDK 会保留 Harness 会话事件，供后续行为评分器使用。

各次运行在重复轮次之间交替模型顺序，并在每次尝试前复制 fixture。确定性评分器决定通过或失败。提供方用量在存在时被保存，在缺失时保持未知。路由决策需要多次重复并检查原始产物，而不能只查看汇总表。

首个套件使用四个小型 Python 维护任务：分页边界、经过验证的 JSON Lines 聚合、HTTP 重试策略，以及不修改输入的递归配置合并。不同的缺陷类型使汇总结果不那么依赖单一实现模式，而紧凑的 fixture 可让重复比较保持低成本。

两条 benchmark 路由都读取 `OPENCODE_GO_API_KEY`，与已安装的 `OpenCode Go (responses)` 提供方一致。这样可避免误用无关的 OpenCode 客户端凭据进行测试，因为其工作区可能具有不同的 Contributor 数据策略同意状态。

## 安全限制

首个版本通过复制 fixture 来隔离工作目录，但不提供操作系统 sandbox（沙箱）。Fixture 不包含凭据或生产状态。在接纳不受信任的模型或敏感代码库之前，必须使用由 sandbox 支持的执行方式。

## 曾考虑的替代方案

**继续使用独立的 OpenCode 实验 runner（运行器）。** 它能保存有用的模型产物，但由 OpenCode 所有的智能体运行时无法将模型质量与智能体运行时行为分离，因此不能衡量模型通过 Peck Harness 的表现。

**将 benchmark 编排放入 agent-loop plugin（智能体循环插件）。** 这会让评分和提供方定价成为运行时职责，尽管两者既不影响模型轮次，也不提供智能体能力。独立的 SDK 消费方可以保持运行时不变。

**使用存放在每个复制 fixture 内的测试进行评分。** 可写模型能够修改这些测试，并在未实现请求行为的情况下获得通过结果。由主机拥有的评分器代码保留在复制工作区之外。

## 后果

Peck Bench 可以通过相同的 Harness 组合比较 OpenCode Go 模型、保留运行证据，并使用模型工作区之外的确定性代码拒绝错误补丁。交替顺序可减少首次运行的系统性偏差，而重复运行可揭示结果差异。

该 benchmark 增加了 Python 编排，并为每种传输协议单独声明提供方路由。复制的工作区不是操作系统沙箱；当提供方事件省略成本时，成本仍保持未知；四个小型 Python fixture 仍不足以支持一般性的模型排名结论。
