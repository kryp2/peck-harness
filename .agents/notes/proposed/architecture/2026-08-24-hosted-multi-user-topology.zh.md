# Agent Note: 将 Peck Harness 托管为钱包登录背后的多用户服务

Status: proposed

[English](2026-08-24-hosted-multi-user-topology.md) | 中文

## Problem

当前唯一运行的 Peck Harness 部署是个人笔记本电脑上的一个 `dsh web` 进程：环回绑定，经 socat 桥接到 WireGuard 内网，默认权限预设为 `danger-full-access`，且没有应用层认证。2026-08-22 的快速审计将其列为 P0：只有当每个 WireGuard 对端都是可信的所有者时，这一设置才站得住脚。邀请真实用户会在三个方面同时打破这个前提：他们需要不依赖 VPN 成员的浏览器访问；需要的工作区不能是宿主机的文件系统；他们的模型用量需要计量。这三样今天都不存在。

两个候选答案按现状都行不通。让云端代理操作用户自己机器上某个目录的连接器在任何仓库中都不存在。UHRP 存储（`storage.peck.to`）是内容寻址的静态检索，无法充当活跃的、随机变更的工作树。

## Proposal

把多用户的 Peck Harness 迁移到托管拓扑：harness 进程运行在自有服务器基础设施上，每个用户获得一个隔离的执行世界，以钱包登录而非 VPN 成员身份进入。

### 拓扑

一个 GCP VM 池（Cloud Run 的请求模型不适合长达数小时的 PTY 代理会话）承载 N 个沙箱化执行世界，每个用户会话一个容器。现有的可移植执行世界接缝无需新的 harness 架构即可提供隔离机制：`fs-e2b` 与 `subprocess-e2b` 把 `ctx.fs`、`ctx.subprocess` 和终端会话放进远程沙箱，而 harness 进程、Cordis 对象、会话持久化和技能留在服务端。裸 `dsh web` GUI 永远不直接暴露；产品前端负责认证，并通过既有的 JSON-RPC/ACP 接口驱动会话。审计建议的启动拒绝机制（非环回可达 + 无认证 + `danger-full-access` 必须拒绝启动）守护此类每一种未来配置。

### 身份与支付流程

钱包登录复用既有组件：`wab` 负责认证交换，BRC-42 身份密钥作为用户标识——这已是 peck.to 的惯例。一次登录将身份映射到托管会话，并映射到经 BRC-100 支付通道授权的消费上限。模型调用按计量路由计划经由 `llm.peck.to` 路由：先预留通道额度再服务，并返回签名收据。网关侧的收据签名验证——审计 P1——是硬性前置条件：在多用户拓扑中，收据就是账单记录，而不仅仅是显示。

### 工作区生命周期

每个沙箱从空状态或用户选择的来源克隆开始。工作树在会话生命周期内只存在于沙箱内部；持久性来自显式的出口而非隐式持久化：把产物导出或发布到 UHRP、把代码推送到 git 远端，或从加密备份（BRC-2）恢复到以后的沙箱。空闲超时后回收沙箱，使成本跟随使用。

### 分期

阶段一是分发计划已定义的付费金丝雀路径，在本拓扑上运行：邀请链接、钱包登录、隔离沙箱、一次带已验证签名收据的计量流式调用。阶段二被显式推迟，即本地工作区桥：用户机器上的一个小型守护进程，向上说 ACP/JSON-RPC，并在本地执行逐操作审批，从而让云端代理可以操作用户拥有的目录。它自身就是一个信任设计产品，只在阶段一证明托管流程之后才启动。

本笔记是对[分发与计量路由计划](2026-08-18-peck-distribution-and-metered-routing.zh.md)的补充：那份计划拥有仓库策略与访问类别；本笔记拥有进程运行的位置以及谁能到达它们。

## Alternatives considered

**把用户邀进 WireGuard 内网。** 不采用：它会把审计的 P0 变成共享攻击面，任何被邀请的对端都能触达以所有者用户运行的未认证主机执行端点。

**用一个未隔离的 harness 进程服务多个用户。** 不采用：会话、插件、凭据和 shell 进程共享进程状态，因此一个用户的任意代码执行就是所有用户的。隔离是产品需求，不是优化。

**用 UHRP 作为工作区存储。** 对活跃工作树不采用，因为 UHRP 是无随机写语义的内容寻址检索。保留它作为围绕沙箱工作区的导出、分享与发布层。

**先建本地工作区连接器。** 在排序上不采用：在服务第一个用户之前，它需要一个受信的本地守护进程、本地审批 UX 和反向传输。云端沙箱更早达到多用户，而且不会比连接器少降低任何风险。

## Acceptance criteria

- 新用户从邀请链接到钱包登录，到隔离的沙箱工作区，再到一次带已验证签名收据的计量模型调用，全程无需 VPN 成员资格、无需本地安装。
- 配置为 `danger-full-access` 的任何 harness 进程在没有应用层认证时不可达；否则启动拒绝机制触发。
- 两个并发用户无法观察彼此的文件、进程或会话。
- 从沙箱出发的工作区出口路径可用：产物导出到 UHRP、代码推送到 git 远端。
- 空闲沙箱自动回收，且计费用量与已开收据对账一致。

## Risks

常驻沙箱即使闲置也产生成本；TTL 回收与按需唤醒可以约束这一点，但会引入冷启动延迟。e2b 适配器家族是实验性 POC；在生产化之前进行加固（沙箱逃逸审查、资源上限、重连行为）是第一位受邀者之前的实际工作。收据验证必须在任何真实聪支付流量之前落地，否则计费显示会大规模失真。笔记本部署仍是开发环境，因此在 Peck 组合层落地之前，它与托管配置之间的组合漂移很可能发生。
